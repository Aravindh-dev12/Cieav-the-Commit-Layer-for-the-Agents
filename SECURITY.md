# CIEAV security model

CIEAV mediates consequential browser actions and treats page content, model output, inferred outcomes, and undo candidates as untrusted until deterministic checks accept them.

## Deterministic authority

Models interpret semantics; deterministic local code controls execution. Model output cannot downgrade deterministic risk or make reversibility more optimistic. Once a consequential interaction is intercepted, control/analysis failure blocks execution rather than failing open.

Cloud inference has no browser replay capability. The local Gateway remains the authority that starts/stops the protected surface, owns provider/control secrets, and requires the durable managed local API in production. Managed production surfaces forcibly disable `CIEAV_TEST_AUTO_APPROVE` and its legacy alias even when inherited from a polluted parent environment.

## Authenticated local control

The browser Control Center is not authorized merely because a request came from loopback. Each protected-surface process receives a fresh random browser-control capability generated by the Gateway. This capability is distinct from the Gateway bearer token, API signing secret, receipt identity, and cloud/model credentials.

Gateway-to-browser control uses the capability as a bearer credential. Interactive Control Center access uses a short-lived, one-time bootstrap nonce exchanged for an `HttpOnly; SameSite=Strict` local session cookie. Unauthenticated Control Center root/API requests fail closed with `401`.

The persistent browser-control capability is not returned by status APIs, persisted as user state, printed by the CLI, or passed into Chromium. Stopping/restarting the protected surface destroys the Gateway's in-memory capability and creates a new one.

## Private browser authority transport

Managed browser control uses Chromium's private `--remote-debugging-pipe` transport rather than a DevTools TCP listener. The Node mediator owns the inherited pipe endpoints and uses browser-wide `Target.setDiscoverTargets` plus flat `Target.attachToTarget` sessions to mediate individual pages.

The managed browser authority path does not expose `--remote-debugging-port`, `/json/list`, `/json/new`, or page WebSocket debugger URLs. Test automation uses authenticated, test-mode-only Control Center endpoints and therefore exercises the same private pipe transport rather than reopening a TCP debugging surface.

This materially reduces local browser-control exposure, but it is still not a sandbox against a fully compromised same-user process capable of inspecting or manipulating CIEAV/Chromium process memory, handles, or the operating system itself.

## Privacy boundary

Every supported remote model egress uses an explicit privacy reducer. URL credentials/query/fragment data, raw form values, full-page text, raw filenames, file contents, and common secret patterns are removed before inference. The Python Cloud provider independently reconstructs an allowlisted packet and refuses non-HTTPS remote Cloud URLs.

Authenticated CIEAV Cloud requests do not follow redirects. CIEAV Cloud independently validates the minimized context and deterministic baseline instead of trusting privacy booleans supplied by the client.

## Local secret storage

Gateway bearer/API/HF and legacy receipt-wrapping secrets use an explicit per-user secret-store abstraction. In automatic mode CIEAV prefers:

- Windows DPAPI bound to the current user,
- macOS Keychain Services,
- Linux Secret Service when an accessible user session/service is available.

Existing plaintext secret files are migrated only after the secure backend successfully writes and reads back the exact value. The plaintext file is removed only after that verification. If an OS secret facility is unavailable, CIEAV falls back explicitly to per-user `0600` files and reports that fallback rather than claiming encryption at rest.

The receipt-v3 Ed25519 private key is itself stored in an AES-256-GCM authenticated envelope. Its wrapping key is derived with scrypt from the per-install receipt secret. Existing plaintext receipt PEM files are migrated only after CIEAV decrypts the new envelope and verifies that it derives the same public key; only then is the plaintext PEM removed. On an OS-backed secret-store installation this removes the long-lived receipt private key from plaintext disk storage. The public receipt key remains non-secret.

These protections are defense in depth, not hardware-backed key isolation. A fully compromised user account or kernel may still recover keys while CIEAV is running.

## Prompt injection

Page text and site-declared semantics are hostile data. CIEAV limits/redacts context, detects common injection patterns, constrains model output, and retains the deterministic minimum. Page content cannot grant authorization, enable a site adapter, or reduce required friction.

## Outcome truth and durability

`COMMITTED` means the approved action entered replay; it does not prove a remote service succeeded. Post-action outcome is separately signed as `OBSERVED_SUCCESS`, `OBSERVED_FAILURE`, or `UNKNOWN`.

HIGH/CRITICAL actions cannot become successful from generic DOM success text alone. Navigation alone does not prove payment, deletion, publication, sharing, permission grant, or upload success.

Outcome finalization remains pending until the local receipt API durably accepts the signed outcome. The mediator serializes duplicate finalization attempts, retries transient local persistence failures with bounded backoff, and exposes pending/persistence-failure state through authenticated local status. Attention/cognitive learning is updated only after the persisted receipt is recovered. During shutdown CIEAV makes a bounded attempt to convert unfinished verification to `UNKNOWN`, persist it, then flush cognitive-state and audit queues before terminating the local API.

A sudden process/OS/power failure can still interrupt work before persistence. Such cases must remain unresolved/unknown rather than being represented as verified success.

## Trusted Undo

One-click Undo requires a signed `OBSERVED_SUCCESS` and a trusted bundled adapter. Generic button labels cannot unlock production Undo. Adapter capabilities are bound to adapter ID/version, exact action type, origin/path rules, expiry, and a deterministic resource fingerprint; the capability is revalidated at execution time.

Compensation/revocation is not described as complete reversal when copies, fees, third-party access, or other effects may persist.

## Receipt and audit integrity

Managed receipt v3 uses a persistent per-user Ed25519 identity. Receipts can be publicly verified from their embedded public key, while the durable store additionally anchors them to the locally enrolled key. Legacy HMAC receipts remain readable for migration.

Audit events use a per-user HMAC-SHA256 chain, cross-rotation linkage, and fsync before replay acknowledgement. `cieav audit verify` checks integrity locally. This is tamper evidence against modification without the local key, not a hardware-backed transparency log.

## Release provenance and platform trust

Release metadata is independently signed with an offline Ed25519 release key. The publish pipeline signs and immediately verifies `manifest.json` and each platform bootstrap metadata file, checks the release public-key ID against an independently configured expected key ID, and never commits the release private key.

Windows production binaries must be Authenticode signed with SHA-256/RFC-3161 timestamping, verified with SignTool/Windows authentication policy, and match the configured signer certificate thumbprint before packaging.

macOS production binaries must be Developer-ID signed with hardened runtime and secure timestamping, pass `codesign --verify`, and the completed macOS runtime ZIP must be accepted by Apple's notary service before publication.

Linux runtime integrity is covered by HTTPS distribution, SHA-256 artifact checks, and independently signed release metadata; distro/package-specific signing can be added if CIEAV later publishes native DEB/RPM packages.

## Bootstrap trust boundary

The public one-line `install.ps1` / `install.sh` bootstrap is initially obtained from the configured CIEAV HTTPS download origin. That first fetch therefore remains rooted in domain/TLS trust. Independent release signatures and platform code signatures protect later release objects and help detect artifact substitution, but they do not make a replaced root installer trustworthy if an attacker fully controls the bootstrap origin.

For that reason production deployment must serve root installers directly without redirects, protect DNS/CDN/origin credentials strongly, use restrictive deployment permissions, retain immutable/versioned artifacts, and monitor unexpected installer changes.

## Release evidence and remaining production operations

The local release verifier redacts known runtime secrets, bearer credentials, token-like query values, and git-remote userinfo from captured evidence. It omits the machine hostname so qualification reports do not unnecessarily identify the user's device.

Before public launch CIEAV still requires actual clean-VM qualification on supported Windows/macOS/Linux targets, real-domain TLS/CDN/cloud deployment, configured signing/notarization credentials, monitoring/rate limits/backups, and successful `npm run release:verify` / cross-platform qualification evidence. No documentation or CI configuration substitutes for those executed release gates.
