# CIEAV security model

CIEAV mediates consequential browser actions and treats page content, model output, inferred outcomes, and undo candidates as untrusted until deterministic checks accept them.

## Deterministic authority

Models interpret semantics; deterministic local code controls execution. Model output cannot downgrade deterministic risk or make reversibility more optimistic. Once a consequential interaction is intercepted, control/analysis failure blocks execution rather than failing open.

Cloud inference has no browser replay capability. The local Gateway remains the authority that starts/stops the protected surface, owns provider/control secrets, and requires the durable managed local API in production.

Managed production surfaces forcibly disable `CIEAV_TEST_AUTO_APPROVE` and its legacy alias even when inherited from a polluted parent environment.

## Authenticated local control

The browser Control Center is not authorized merely because a request came from loopback. Each protected-surface process receives a fresh random browser-control capability generated by the Gateway. This capability is distinct from the Gateway bearer token, API signing secret, receipt identity, and cloud/model credentials.

Gateway-to-browser control uses the capability as a bearer credential. Interactive Control Center access uses a short-lived, one-time bootstrap nonce which is exchanged for an `HttpOnly; SameSite=Strict` local session cookie. Unauthenticated Control Center root/API requests fail closed with `401`.

The persistent browser-control capability is not returned by status APIs, persisted as user state, printed by the CLI, or passed into Chromium. The mediator removes current and legacy browser-control environment variables before spawning the browser. Stopping/restarting the protected surface destroys the Gateway's in-memory capability and creates a new one for the next surface.

This is defense in depth against accidental and unauthenticated local access; it is not a claim that secrets are safe from a fully compromised same-user OS process capable of inspecting another process's memory or launch environment.

## Browser isolation and replay

CIEAV uses a dedicated Chromium profile and isolated-world mediator. Approved top-frame click replay is coordinate-bound, one-shot, and short-lived. Chromium never receives Gateway bearer credentials, browser-control credentials, model provider credentials, API-signing secrets, receipt private keys, or audit-integrity keys.

The current implementation still uses loopback Chrome DevTools Protocol transport. Loopback reduces network exposure but is not as strong as a private inherited pipe. Chromium officially supports `--remote-debugging-pipe`; on POSIX this uses dedicated descriptors and on Windows Chromium requires explicit inherited pipe handles. A correct cross-platform migration therefore needs tested transport/handle plumbing rather than a flag-only change. Until that migration is qualified on supported platforms, CIEAV does not claim same-user-process isolation for CDP.

## Privacy boundary

Every supported remote model egress uses an explicit privacy reducer. URL credentials/query/fragment data, raw form values, full-page text, raw filenames, file contents, and common secret patterns are removed before inference. The Python Cloud provider independently reconstructs an allowlisted packet and refuses non-HTTPS remote Cloud URLs.

Authenticated CIEAV Cloud requests do not follow redirects. CIEAV Cloud independently validates the minimized context and deterministic baseline instead of trusting privacy booleans supplied by the client.

## Prompt injection

Page text and site-declared semantics are hostile data. CIEAV limits/redacts context, detects common injection patterns, constrains model output, and retains the deterministic minimum. Page content cannot grant authorization, enable a site adapter, or reduce required friction.

## Outcome truth and durability

`COMMITTED` means the approved action entered replay; it does not prove a remote service succeeded. Post-action outcome is separately signed as `OBSERVED_SUCCESS`, `OBSERVED_FAILURE`, or `UNKNOWN`.

HIGH/CRITICAL actions cannot become successful from generic DOM success text alone. Navigation alone does not prove payment, deletion, publication, sharing, permission grant, or upload success.

Outcome finalization remains pending until the local receipt API durably accepts the signed outcome. The mediator serializes duplicate finalization attempts, retries transient local persistence failures with bounded backoff, and exposes pending/persistence-failure state through authenticated local status. Attention/cognitive learning is updated only after the persisted receipt is recovered. During shutdown CIEAV makes a bounded attempt to convert unfinished verification to `UNKNOWN`, persist it, then flush cognitive-state and audit queues before terminating the local API.

This bounded shutdown behavior improves crash/shutdown resilience but is not an fsync guarantee against sudden power loss before the local API accepts the outcome; such cases must remain semantically unresolved rather than being represented as verified success.

## Trusted Undo

One-click Undo requires a signed `OBSERVED_SUCCESS` and a trusted bundled adapter. Generic button labels cannot unlock production Undo. Adapter capabilities are bound to adapter ID/version, exact action type, origin/path rules, expiry, and a deterministic resource fingerprint; the capability is revalidated at execution time.

Compensation/revocation is not described as complete reversal when copies, fees, third-party access, or other effects may persist.

## Receipt and audit integrity

Managed receipt v3 uses a persistent per-user Ed25519 keypair. Receipts can be publicly verified from their embedded public key, while the durable store additionally anchors them to the locally enrolled key. Legacy HMAC receipts remain readable for migration.

The Ed25519 private key is filesystem-protected, not hardware-backed. A fully compromised OS account may obtain it.

Audit events use a per-user HMAC-SHA256 chain, cross-rotation linkage, and fsync before replay acknowledgement. `cieav audit verify` checks integrity locally. This is tamper evidence against modification without the local key, not a hardware-backed transparency log.

## Local services

Gateway, local API, and Control Center bind to loopback; Control Center APIs additionally require the per-surface browser-control capability/session described above. The current CDP endpoint remains loopback-only but unauthenticated by Chromium itself, so a sufficiently capable same-user local process remains inside the current CDP threat boundary.

Loopback is not a sandbox and must not be described as OS-level isolation. The planned private CDP transport is a release-hardening item, especially for Windows where correct inherited-HANDLE setup must be verified in clean VMs.

## Release evidence and distribution

The local release verifier redacts known runtime secrets, bearer credentials, token-like query values, and git-remote userinfo from captured evidence. It omits the machine hostname so qualification reports do not unnecessarily identify the user's device.

Installers require HTTPS-controlled distribution, SHA-256 artifact verification, same-origin bootstrap/runtime downloads, redirect rejection, and transactional rollback. A final production release still needs real-domain TLS/CDN deployment, independently signed release provenance/manifests, platform code signing/notarization where applicable, monitoring, backups, and operational rate limits.
