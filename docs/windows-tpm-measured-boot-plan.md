# Windows TPM measured-boot attestation plan

This document defines the next Windows TPM assurance increment after native key attestation. It is intentionally a design/acceptance contract, not a claim that measured boot is already implemented.

## Why this is separate from key attestation

CIEAV's native Windows key-attestation lane proves that the exact release keys are bound to the TPM/AIK trust path. It does not, by itself, prove the machine's boot state.

Windows exposes separate platform-attestation evidence for PCR state. Microsoft Azure Attestation's documented TPM/VBS protocol describes:

- an AIK certificate and AIK public key;
- a `current_claim` generated by `NCryptCreateClaim` with `dwClaimType = NCRYPT_CLAIM_PLATFORM` and a PCR mask, with the service challenge included for freshness;
- a `boot_claim` for boot-time PCR state;
- Windows Boot Configuration Log / TCG event logs retrieved with `Tbsi_Get_TCG_Log_Ex`.

CIEAV must therefore treat key attestation and measured-boot/platform-state attestation as two evidence classes.

## Research status — 2026-08-21

The current research pass established the following implementation facts before production collector code is allowed to emit measured-boot evidence:

1. Microsoft documents the Azure TPM/VBS `current_claim` as the result of `NCryptCreateClaim` with `dwClaimType = NCRYPT_CLAIM_PLATFORM`, `NCRYPTBUFFER_TPM_PLATFORM_CLAIM_PCR_MASK`, and the service challenge included in the claim computation.
2. Microsoft documents the corresponding `boot_claim` as a platform claim for PCR state at boot without the current challenge freshness semantics.
3. Current Windows SDK metadata defines `NCRYPTBUFFER_TPM_PLATFORM_CLAIM_PCR_MASK = 80`, `NCRYPTBUFFER_TPM_PLATFORM_CLAIM_NONCE = 81`, and `NCRYPTBUFFER_TPM_PLATFORM_CLAIM_STATIC_CREATE = 82`.
4. Current Windows SDK metadata defines `NCRYPT_TPM_PLATFORM_ATTESTATION_STATEMENT` as exactly six 32-bit fields: `Magic`, `Version`, `pcrAlg`, `cbSignature`, `cbQuote`, and `cbPcrs`.
5. The SDK platform-attestation magic is `NCRYPT_PLATFORM_ATTEST_MAGIC = 0x44504150`; the statement version is `0`.
6. `Tbsi_Get_TCG_Log_Ex(TBS_TCGLOG_SRTM_CURRENT)` returns the WBCL associated with PCR 0-15 for the current boot/resume session. `TBS_TCGLOG_SRTM_BOOT` returns the most recent clean-boot SRTM log.
7. Microsoft documents that a crypto-agile WBCL starts with a legacy-format event whose event data has the null-terminated `Spec ID Event03` signature and algorithm/digest-size table. Subsequent events are TCG PCR Event2 records.
8. Microsoft's open TSS.MSR WBCL parser bounds the number of digests, validates descriptor/event lengths, selects SHA-256 when present, and reconstructs software PCR values from the event log. CIEAV independently implements the same security properties rather than importing that code.
9. The public `NCryptCreateClaim` documentation does not specify the exact subject/authority handle pairing required for `NCRYPT_CLAIM_PLATFORM`. CIEAV therefore will not guess this contract in production code.
10. A separate read-only diagnostic probe now exists to test plausible handle combinations on the physical TPM. It does not create/delete/finalize keys and cannot emit measured-boot `VERIFIED`.

The current TypeScript module `apps/api/src/windows-tpm-measured-boot.ts` implements strict platform-statement parsing, strict TCG2/WBCL parsing, SHA-bank PCR replay, and selected-PCR digest omission failure. Its focused tests exercise malformed magic/version, truncation, duplicate algorithms, forged digest sizes, undeclared/duplicate event digest algorithms, selected-bank omission, invalid masks and incomplete PCR tables.

The diagnostic executable lives in `native/windows-tpm-measured-boot-probe`. It intentionally leaves the already physically qualified native key-attestation bridge unchanged, because changing those bytes would invalidate the recorded key-attestation qualification hash.

## Required evidence

The future local measured-boot lane must collect, at minimum:

1. The same pinned AIK certificate and AIK public key used by native key attestation.
2. A fresh verifier-generated challenge/nonce.
3. A current PCR platform claim generated with `NCRYPT_CLAIM_PLATFORM`.
4. An explicit PCR selection/mask. The selection must be policy-controlled; it must never be silently inferred from arbitrary caller input.
5. The SRTM current/boot WBCL retrieved through `Tbsi_Get_TCG_Log_Ex`.
6. If DRTM is required by policy, its corresponding current/boot log. Absence of DRTM must not be silently interpreted as a DRTM PASS.
7. The raw platform claim and event-log digests in the persisted evidence digest.

## Verification requirements

CIEAV must not emit platform-state `VERIFIED` merely because Windows returned a platform-claim blob.

A verifier must establish all of the following:

- the claim is signed by the expected pinned AIK;
- the challenge/nonce is bound to the claim and exactly matches the verifier-generated value;
- the quoted PCR selection exactly matches the policy-selected PCR mask;
- the quote/hash algorithm is allowed by policy (SHA-256 should be required for the release policy unless a stronger explicitly supported bank is selected);
- the PCR values embedded/bound by the platform claim are structurally valid;
- the WBCL parses without truncation, integer overflow, ambiguous digest lengths, duplicate malformed algorithm declarations, or trailing-data ambiguity;
- replaying the selected WBCL events into clean PCR values reproduces the quoted PCR values for the selected bank;
- Secure Boot and other boot assertions are derived from replayed measured events / policy, not from an unrelated OS boolean;
- freshness, AIK identity, event-log digest, PCR selection and resulting PCR digest are persisted into the final attestation claims digest.

If any of these checks is unavailable, ambiguous, unsupported, or inconsistent, the platform-state result must fail closed.

## Windows APIs and structures

The implementation is expected to use Windows' documented interfaces rather than a private TPM command transport where possible:

- `NCryptCreateClaim`
- `NCRYPT_CLAIM_PLATFORM`
- `NCRYPTBUFFER_TPM_PLATFORM_CLAIM_PCR_MASK`
- `NCRYPTBUFFER_TPM_PLATFORM_CLAIM_NONCE`
- `NCRYPTBUFFER_TPM_PLATFORM_CLAIM_STATIC_CREATE` where boot/static claim semantics require it
- `NCRYPT_TPM_PLATFORM_ATTESTATION_STATEMENT`
- `Tbsi_Get_TCG_Log_Ex`
- `TBS_TCGLOG_SRTM_CURRENT`
- `TBS_TCGLOG_SRTM_BOOT`
- DRTM log types only when the deployment policy actually requires DRTM

Microsoft documents `NCRYPT_TPM_PLATFORM_ATTESTATION_STATEMENT` as containing the TPM signature, TPM quote and raw PCR values. CIEAV should parse all lengths with strict bounds before processing any nested TPM structure.

## Parser requirements

The WBCL parser is security-sensitive and must be treated as an untrusted binary parser even though its immediate source is the local OS.

Required parser properties:

- bounded total input size;
- checked arithmetic for every offset and length;
- support for the initial `Spec ID Event03` algorithm table;
- digest-size lookup only from a validated algorithm table;
- reject unknown algorithms when they occur in the policy-selected PCR bank instead of guessing digest sizes;
- reject truncated events and impossible event sizes;
- exact end-of-buffer consumption unless a documented format explicitly permits padding;
- deterministic replay of `PCR := HASH(PCR || eventDigest)` for the selected bank;
- no use of event display strings as trust decisions without validating the corresponding measured digest/event semantics.

Fuzz/property tests should exercise the parser before it is used in the production qualification gate.

## Diagnostic hardware probe

The diagnostic measured-boot probe is intentionally read-only. It:

- opens the existing AIK through `Microsoft Platform Crypto Provider`;
- requires the provider to report hardware implementation without software implementation;
- generates a fresh 32-byte nonce;
- requests an SRTM PCR mask of `0x0000FFFF` (PCR 0-15);
- probes `Tbsi_Get_TCG_Log_Ex` for both current and clean-boot SRTM WBCLs;
- performs only size-query `NCryptCreateClaim` calls for three plausible subject/authority handle combinations;
- reports raw Windows status codes and required claim sizes;
- never creates, finalizes, rotates or deletes TPM keys.

The output is discovery evidence only. A successful combination must still be implemented as a pinned collector and followed by independent quote signature, nonce, PCR selection and WBCL replay verification before measured boot can be `VERIFIED`.

## Release policy

The first production measured-boot policy should be narrow and versioned. It should define:

- PCR mask;
- accepted hash bank(s);
- whether SRTM-only is acceptable;
- whether DRTM is required;
- required Secure Boot-related measurements;
- whether BitLocker/device-encryption measurements are informational or policy-bearing;
- maximum evidence age;
- policy identifier/version recorded in the attestation.

A policy change must produce a new policy identifier. CIEAV should never reinterpret old evidence under a new policy without re-attesting.

## Assurance boundary

A fully implemented and locally verified measured-boot lane would improve the native Windows assurance from "exact TPM-bound keys under a pinned AIK" to "exact TPM-bound keys plus locally verified PCR/event-log boot state."

It would still be local attestation. An independent remote verifier such as MAA provides a different trust boundary because the verifier is not running in the same Windows instance that produced the evidence.

Until the parser, quote verification, event-log replay, policy evaluation and physical hardware tests all pass, CIEAV must continue to report measured boot as **not qualified**.
